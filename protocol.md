# Протокол формирования внешнего датасета Bethesda v1

## 1. Назначение

Цель формирования внешнего датасета — проверка способности ранее разработанной системы классификации биомедицинских текстов переноситься на независимые данные, не использовавшиеся при обучении и подборе гиперпараметров модели.

Внешний датасет формируется из открытых источников и должен содержать текстовые цитологические описания образцов щитовидной железы, полученных методом тонкоигольной аспирационной биопсии, с известной категорией по системе Bethesda I–VI.

Сформированный набор данных используется исключительно для внешнего тестирования зафиксированной базовой модели. До завершения первичного тестирования модель не дообучается и ее параметры не изменяются.

## 2. Критерии включения

В датасет включается случай, если одновременно выполняются следующие условия:

1. Представлено текстовое цитологическое описание материала щитовидной железы.
2. Исследование относится к тонкоигольной аспирационной биопсии щитовидной железы.
3. Для случая однозначно указана категория Bethesda от I до VI.
4. Текст содержит достаточное описание цитологических или морфологических признаков для выполнения классификации.
5. Источник случая доступен для последующей проверки.
6. Случай ранее не использовался при обучении исходной модели.
7. Текст не содержит персональных данных пациента либо такие данные могут быть полностью исключены без потери диагностического содержания.

## 3. Критерии исключения

Не включаются:

* случаи без установленной категории Bethesda;
* материалы, содержащие только результаты ультразвукового исследования;
* данные, представленные только в виде изображений без текстового описания;
* гистологические заключения без соответствующего цитологического описания;
* табличные клинические признаки без свободного текста;
* синтетические или автоматически сгенерированные заключения;
* дубликаты ранее добавленных случаев;
* тексты, в которых после удаления явного указания категории Bethesda практически не остается диагностической информации;
* случаи, для которых невозможно достоверно установить источник или правильную метку.

## 4. Структура записи

Для каждого случая сохраняются следующие поля:

| Поле             | Описание                                    |
| ---------------- | ------------------------------------------- |
| `case_id`        | уникальный идентификатор записи             |
| `bethesda_label` | категория Bethesda I–VI                     |
| `raw_text`       | исходный текст из источника                 |
| `model_text`     | текст, подготовленный для передачи модели   |
| `source_title`   | название публикации или источника           |
| `source_url`     | ссылка на источник                          |
| `source_year`    | год публикации                              |
| `source_type`    | тип источника                               |
| `language`       | язык текста                                 |
| `notes`          | дополнительные замечания                    |
| `include`        | признак включения записи в итоговую выборку |

Основной файл набора данных формируется в формате CSV.

## 5. Правила обработки текста

Исходный текст сохраняется в поле `raw_text` без смысловых изменений.

Отдельно формируется поле `model_text`, предназначенное непосредственно для тестирования модели.

Перед формированием `model_text` необходимо удалить:

* прямое указание категории Bethesda;
* формулировки вида `Bethesda III`, `category IV`, `class V` и аналогичные;
* служебную информацию, непосредственно раскрывающую целевую метку;
* персональные данные пациента;
* элементы текста, не относящиеся к цитологическому заключению.

После этого применяется тот же алгоритм предобработки, который использовался при создании исходной системы классификации.

Специальная предобработка, разработанная только для повышения результатов на внешнем датасете, до завершения первого тестирования не применяется.

## 6. Контроль утечки целевой информации

Перед включением каждого случая необходимо проверить, что текст, подаваемый модели, не содержит явного ответа.

Особое внимание уделяется словам и конструкциям:

* `Bethesda`;
* `category`;
* `class`;
* обозначениям категорий I–VI;
* формулировкам, непосредственно сообщающим итоговый диагноз в качестве классификационной метки.

При этом медицинские признаки, являющиеся частью самого цитологического описания, не должны автоматически удаляться только потому, что они характерны для определенной категории.

Сомнительные случаи помечаются для ручной проверки.

## 7. Баланс классов

На первом этапе планируется сформировать пилотную выборку примерно по 10 случаев для каждой категории Bethesda.

Целевой объем основной внешней выборки:

**30–50 случаев на каждый класс**, то есть ориентировочно **180–300 текстов**.

Преднамеренное выравнивание количества примеров между классами допускается, поскольку набор формируется как исследовательский benchmark для проверки качества классификации, а не как выборка, отражающая реальную распространенность категорий Bethesda.

## 8. Разнообразие источников

Следует по возможности избегать формирования всего датасета на основе одной публикации или одного медицинского учреждения.

При сборе учитываются:

* количество независимых публикаций;
* количество медицинских учреждений;
* годы публикации;
* особенности оформления заключений;
* язык исходных текстов.

Предпочтение отдается случаям из разных независимых источников.

## 9. Язык данных

Основной внешний датасет желательно формировать из русскоязычных текстов, поскольку исходная модель обучалась на русскоязычном корпусе.

Англоязычные данные при необходимости формируются как отдельная выборка и рассматриваются как отдельный эксперимент по межъязыковому переносу модели.

Результаты русскоязычной и англоязычной внешней валидации не объединяются в одну итоговую метрику.

## 10. Фиксация версии датасета

После завершения сбора, очистки, проверки меток и удаления дубликатов формируется зафиксированная версия:

`dataset_external_v1.csv`

После фиксации состава выборки выполняется первый запуск базовой модели.

Изменять состав тестовой выборки на основании полученных предсказаний модели не допускается.

Если в процессе проверки обнаружена объективная ошибка в метке или обработке текста, изменение фиксируется отдельно с указанием причины.

## 11. Первичная внешняя проверка

Для первой валидации используется текущая зафиксированная версия модели без дополнительного обучения и изменения гиперпараметров.

Для внешнего датасета рассчитываются:

* Accuracy;
* Macro-F1;
* Weighted-F1;
* Precision, Recall и F1-score для каждого класса;
* матрица ошибок;
* количество объектов каждого класса.

Дополнительно сохраняются предсказания модели для каждого отдельного текста.

## 12. Интерпретация результатов

Если качество модели на независимых данных остается близким к результатам на исходном датасете, делается вывод об устойчивости разработанного подхода к изменению источника данных.

При существенном снижении качества проводится отдельный анализ причин деградации, включающий:

* анализ ошибок по классам;
* исследование различий лексики;
* сравнение длины и структуры текстов;
* анализ распределения классов;
* исследование особенностей оформления заключений;
* анализ различий между исходным и внешним корпусами.

Только после этого формулируются гипотезы по совершенствованию системы и проводится следующий этап экспериментов.

## 13. Воспроизводимость

Для каждого включенного объекта должен сохраняться источник происхождения данных.

Процесс формирования внешнего датасета должен позволять восстановить:

1. откуда получен исходный текст;
2. какая категория Bethesda ему соответствует;
3. какие преобразования были выполнены;
4. почему запись была включена или исключена;
5. какая версия датасета использовалась при конкретном эксперименте.

Если лицензия источника не позволяет распространять полный текст, в публичной версии проекта сохраняются только допустимые данные и информация, необходимая для идентификации исходного источника.
